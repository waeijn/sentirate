# System Architecture

SentiRate is designed as a highly scalable, decoupled middleware layer. Rather than embedding security logic directly into an organization's core application, this system sits in front of the API, intercepting and evaluating traffic in real-time. This architecture is specifically optimized for API-dependent enterprises and infrastructure operators.

---

## 1. The IPO (Input-Process-Output) Model

The system operates on a strict Input-Process-Output framework to ensure separation of concerns and ultra-low latency.

### Input
* **Client Metadata:** Incoming HTTP requests are intercepted by the middleware. The system extracts the Client IP address and the exact timestamp of the request.
* **Administrator Configuration:** System parameters (bucket sizes, heuristic thresholds) defined by the network administrator.

### Process
1. **Inline Fast Gate:** An immediate check against a 1-second rolling window to instantly drop mechanically impossible volumetric floods (>30 RPS).
2. **Metric Accumulation:** The request timestamp is logged into a lightweight Redis sliding window.
3. **Background Heuristic Evaluation:** Asynchronous workers calculate Request Rate ($\lambda$), Interval Regularity ($\sigma$), and Burst Frequency to classify the IP without blocking the main event loop.
4. **Atomic Enforcement:** A Lua script executes inside Redis to deduct tokens from the dynamically sized Token Bucket.

### Output
* **Traffic Disposition:** The middleware either forwards the request to the upstream application (`HTTP 200 OK`) or halts it at the edge (`HTTP 429 Too Many Requests`).
* **Telemetry Data:** Enforcement actions and system health metrics are broadcasted via Socket.IO to the Visual Dashboard.

## 2. Core Components

### 2.1 FastAPI (The Reverse Proxy)
Built on Python's ASGI framework, FastAPI provides the asynchronous event loop necessary to handle thousands of concurrent connections. It acts as the gateway, ensuring that the heavy math required for heuristic evaluation is offloaded to background tasks rather than blocking incoming user requests.

### 2.2 Redis (The Source of Truth)
Unlike basic rate limiters that store state in application memory (which is lost on restart and doesn't scale), SentiRate relies entirely on Redis.
* **Atomic Lua Scripting:** Token bucket validation (checking capacity, calculating refill, and deducting a token) must happen simultaneously. By executing this inside a Redis Lua script, the system prevents "race condition" bypasses where two concurrent requests drain the same token.
* **Durability (AOF):** Redis is configured with Append-Only File (AOF) persistence (`appendfsync everysec`). Every heuristic calculation and token bucket state is written to disk every second, ensuring the system can recover instantly from a server crash without dropping its memory of active attackers.
* **Memory Management:** Textual audit logs are strictly capped via `LTRIM` to prevent memory bloat, allowing the middleware to maintain an $O(1)$ constant memory footprint even under extreme load.

### 2.3 Visual Monitoring Dashboard
A React and TypeScript frontend that consumes Socket.IO events to render live traffic data. It provides administrators with real-time visibility into System Throughput, Request Acceptance Rate (RAR), and a live audit trail of heuristic decisions generated by the **Feedback Provider**.
